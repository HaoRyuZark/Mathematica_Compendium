\chapter{Relational Algebra}

\section{Relations In Set Theory}

In mathematics, a \emph{relation} is a set formed from the Cartesian product of two sets. It contains ordered pairs \((a,b)\).

\subsection{The Cartesian Product for Relation Algebra}

The Cartesian Product for our entities is defined as:

\[
    S \times T := \bigcup_{(s_1, \dots, s_n) \in S} \left[ \bigcup_{(t_1, \dots, t_k) \in T} \{(s_1, \dots, s_n, t_1, \dots, t_k)\}\right]
\]

Simplified: each element of \(S\) is combined with each element of \(T\). The size of this
special product is \( |S \times T| = |S| \cdot |T| \).

In relational algebra, relations represent tables and their rows are the tuples.

\section{Relational Algebra}

Relational Algebra is a \emph{formal, procedural query language} for the relational model. It provides a set of operators that take relations (tables) as input and produce relations as output.

\subsection{Axioms of Relational Algebra}

Relational Algebra is based on \emph{set theory} and satisfies the following axioms:

\begin{itemize}

    \item \emph{Closure}: Every operation produces a relation.

    \item \emph{Set Semantics}: Relations do not contain duplicate tuples.

    \item \emph{Order Irrelevance}: The order of tuples and attributes does not matter.

    \item \emph{Composability}: Operations can be nested arbitrarily.

\end{itemize}

\textbf{Example:}
  
If \(\sigma_{id > 1}(A)\) returns a relation, it can be used as input to another operator such as projection.

\section{Relations In Relational Algebra}

In database theory, a \emph{relation} is a finite set of tuples over a fixed set of attributes.

Formally:

\[
    R \subseteq D_1 \times D_2 \times \dots \times D_n
\]

\textbf{Example:}
  
Relation \(A(id, value)\) is a set of tuples:

\[
    A = \{(1, X), (2, Y)\}
\]

\subsection{Identifier and Schema}

We define:

\[
    \mathrm{ident}(R) = \{a_i\}_i \quad \text{and} \quad \mathrm{schema} (R) = \{[a_1:T_1, \dots, a_n:T_n]\}.
\]

\(\mathrm{ident}\) returns the names of the attributes of the relation, while \(\mathrm{schema}\) returns the attributes and their corresponding types.

\subsection{Domain of an Attribute}

The \emph{domain} of an attribute \(a\) in a relation \(R\) is the set of all possible values that \(a\) can take in \(R\).

\section{Relational Algebra Operations}

\subsection{Cartesian Product for Relations}

The \emph{Cartesian product} combines every tuple of one relation with every tuple of another.
This is also called the \emph{cross join} is some implementations.

\[
    S \times T = \bigcup_{(s_1, \dots, s_n) \in S} \left[ \bigcup_{(t_1, \dots, t_n) \in T} \{(s_1, \dots, s_n, t_1, \dots, t_k)\} 
    \right]
\]

With size \(|S \times T|  = |S| \times |T|\).

\textbf{Example:}

\begin{verbatim}
    SELECT * FROM T, S;
    -- or equivalently:
    SELECT * FROM T CROSS JOIN S;
\end{verbatim}

\subsection{Union \texorpdfstring{\((\cup)\)}{}}

Combines tuples from two relations with the \emph{same schema} (same columns).

\[
    A \cup B
\]

For the union of relations they have to be \emph{union compatible} which means:

\begin{itemize}

    \item They have the same numbers of elements in the tuple. 

    \item The relations need to have the same columns.

\end{itemize}

\textbf{Example:}

\begin{verbatim}
    SELECT * FROM T
    UNION
    SELECT * FROM S;
\end{verbatim}

\subsection{Set Difference \texorpdfstring{\((\setminus)\)}{}}

Returns tuples in one relation but not in another.

\[
    A \setminus B
\]

\textbf{Example:}

\begin{verbatim}
    SELECT * FROM T
    EXCEPT
    SELECT * FROM S;
    -- or in some SQL dialects:
    SELECT * FROM T
    MINUS
    SELECT * FROM S;
\end{verbatim}

\subsection{Intersection \texorpdfstring{\(\cap\)}{}}

Returns tuples common to both relations.

\[
    A \cap B = A \setminus (A \setminus B)
\]

\textbf{Example:}

\begin{verbatim}
    SELECT * FROM T
    INTERSECT
    SELECT * FROM S;
\end{verbatim}

\subsection{Selection \texorpdfstring{\(\sigma\)}{}}

Filters tuples based on a predicate.

\[
    \sigma_{\theta}(S) = \{s \in S \mid s \text{ satisfies } \Theta\}
\]

\textbf{Example:}

\begin{verbatim}
    SELECT * FROM T WHERE a > 10;
\end{verbatim}

\subsection{Projection \texorpdfstring{\(\pi\)}{}}

Selects specific attributes.

\[
    \prod_{a_{i1}, \dots, a_{ik}}(S) \{(a_{i1}, \dots, a_{ik}) \mid a \in S\}
\]

This gives us the same tuples of the original relational but only with the columns we selected. 

It can also be noted as \(\pi\).

\textbf{Example:}

\begin{verbatim}
    SELECT a, b FROM T;
\end{verbatim}

\subsection{Symmetric Difference \texorpdfstring{\(\triangle\)}{}}

Tuples in either relation but not in both.

\[
    A \triangle B = (A \setminus B) \cup (B \setminus A)
\]

\textbf{Example:}

\begin{verbatim}
    (SELECT * FROM T EXCEPT SELECT * FROM S)
    UNION
    (SELECT * FROM S EXCEPT SELECT * FROM T);
\end{verbatim}

\subsection{Rename \texorpdfstring{\(\rho\)}{}}

Renames relations or attributes.

\[
    \rho_{A'(key, data)}(A)
\]

\textbf{Example:}

\begin{verbatim}
    SELECT a AS x, b AS y, c AS z FROM T;
    -- or rename the table:
    SELECT * FROM T AS T_new;
\end{verbatim}

\subsection{\texorpdfstring{\(\mathrm{with}\)}{with}}

\(\mathrm{with}\) allows us to store products of specific operation with a special name which can be used later in other operations.

\subsection{Join \texorpdfstring{\(\bowtie\)}{}}

It is a \emph{theta/inner join} is the Cartesian product plus a selection based on a condition \(\theta\).

\[
    S \bowtie_{\theta } T = \sigma_\theta (S \times T)
\]

\textbf{Example:}

\begin{verbatim}
    SELECT * FROM T INNER JOIN S ON T.a = S.d;
    -- or with theta condition:
    SELECT * FROM T INNER JOIN S ON T.a < S.d;
\end{verbatim}  

\subsection{Equi-Join}

An \emph{equi-join} is a join where the join condition consists only of equality comparisons between attributes of the two relations.

\[
    R \bowtie_{R.a_1 = S.b_1 \land \dots \land R.a_k = S.b_k} S.
\]

The name and domain of the attributes must be the same.

\[
    R \bowtie_{R.a_1 = S.b_1 \land \dots \land R.a_k = S.b_k} S = \sigma_{R.a_1 = S.b_1 \land \dots \land R.a_k = S.b_k}(R \times S)
\]

\textbf{Example:}

\begin{verbatim}
    SELECT * FROM T JOIN S ON T.a = S.d AND T.b = S.e;
\end{verbatim}

\subsection{Natural Join}

It is a special case of the equi-join which can only be performed only if there is a common attribute.

\[
    R \bowtie S
\]

Let \(C = \mathrm{ident}(R) \cap \mathrm{ident}(S)\) be the common attributes.

\[
    R \bowtie S = \pi_{\mathrm{ident}(R) \cup \mathrm{ident}(S)}\left(\sigma_{\bigwedge_{c \in C} R.c = S.c}(R \times S)\right)
\]

\textbf{Example:}

\begin{verbatim}
    SELECT * FROM T NATURAL JOIN S;
    -- assumes T and S have common column names
\end{verbatim}

\subsection{Semi-Join}

It is a case were we only care about the attribute names but not its values.

\[
    R \ltimes S
\]

\[
    R \ltimes S = \pi_{\mathrm{ident}(R)}(R \bowtie S)
\]

Or alternatively:

\[
    R \ltimes S = \pi_{\mathrm{ident}(R)}\left(\sigma_{\bigwedge_{c \in C} R.c = S.c}(R \times S)\right)
\]

where \(C = \mathrm{ident}(R) \cap \mathrm{ident}(S)\).

\textbf{Example:}

\begin{verbatim}
    SELECT T.* FROM T WHERE EXISTS 
    (SELECT 1 FROM S WHERE T.a = S.d);
    -- or using IN:
    SELECT * FROM T WHERE a IN (SELECT d FROM S);
\end{verbatim}

\subsection{Anti Semi-Join}

In this case, it works very similar to the semi join, but we take the attributes which do not participate in the natural join.

\[
    R \triangleright S
\]

\[
    R \triangleright S = R \setminus (R \ltimes S) = R \setminus \pi_{\mathrm{ident}(R)}(R \bowtie S)
\]

\textbf{Example:}

\begin{verbatim}
    SELECT T.* FROM T WHERE NOT EXISTS (SELECT 1 FROM S WHERE T.a = S.d);
    -- or using NOT IN:
    SELECT * FROM T WHERE a NOT IN (SELECT d FROM S);
\end{verbatim}

\subsection{Outer Join}

The \emph{outer join} preserves non-matching tuples.

\begin{itemize}
    \item \emph{Left Outer Join}: It returns all tuples from the left relation with not matches on the right. 
    \item \emph{Right Outer Join}: It returns all tuples from the right relation with not matches on the left.
    \item \emph{Full Outer Join}: It returns all tuples from both relations which are not in the inner join.
\end{itemize}

\textbf{Example:}

\begin{verbatim}
    -- Left Outer Join:
    SELECT * FROM T LEFT OUTER JOIN S ON T.a = S.d;

    -- Right Outer Join:
    SELECT * FROM T RIGHT OUTER JOIN S ON T.a = S.d;

    -- Full Outer Join:
    SELECT * FROM T FULL OUTER JOIN S ON T.a = S.d;
\end{verbatim}

\subsection{Division \texorpdfstring{\(\div\)}{}}

Used to express \emph{"for all"} queries. It can only be performed when 
the relation on the right is a proper subset of the left relation.

Let

\begin{itemize}
    \item \(R(X, Y)\)
    
    \item \(S(Y)\)
\end{itemize}

Then:

\[
    R \div S = \{x \mid \forall y \in S: (x, y) \in R\}
\]

\[
    R \div S = \pi_{X}(R) \setminus \pi_{X}\left((\pi_{X}(R) \times S) \setminus R\right),
\]

where \(X = \mathrm{ident}(R) \setminus \mathrm{ident}(S)\).

\textbf{Example Concept}  

If \(A(id, value)\) contains all values in \(B(value)\), division returns the corresponding ID's.

\begin{verbatim}
    -- Find tuples in T that match all tuples in S
    SELECT DISTINCT T.a FROM T 
    WHERE NOT EXISTS (
    SELECT S.d FROM S 
    WHERE NOT EXISTS (
        SELECT * FROM T AS T2 
        WHERE T2.a = T.a AND T2.b = S.d
    )
    );
\end{verbatim}

\subsection{Assignment \texorpdfstring{\((=)\)}{}}

This is just using a placeholder to store the result of a relational algebra operation.

\textbf{Example:}

\begin{verbatim}
    -- Create a view or temporary table
    CREATE VIEW Result AS SELECT * FROM T WHERE a > 5;
    -- or
    CREATE TEMPORARY TABLE Result AS SELECT * FROM T WHERE a > 5;
\end{verbatim}

\section{Types of Keys}

A \emph{key} is an attribute or combination of attributes (composite key) which uniquely identifies an entity.

\begin{itemize}

    \item \emph{Candidate Key:} The term refers to the attributes which are suited for being the key.

    \item \emph{Irreducible:} A key has to be as atomic as possible.

    \item \emph{Super key:} It consists of a candidates key's attributes + potentially some extra attributes.

    \item \emph{Alternate Key:} This is an alternative primary key. This means that the UNIQUE constraints will be imposed on the attribute/s.

    \item \emph{Surrogate Key:} This key has only meaning inside the database. Example: ID \(\to\) Person's Name.

    \item \emph{Foreign Key} This key is an attribute of one table which references another table.

\end{itemize}

\section{Relation Schema}

The \((\mathcal{R}, \tau)\) represents a \emph{relation schema}. We can constrain our relations to obey certain rules. Thus, limiting our space. 
Here, \(\mathcal{R}\) is the set of all relations of \(n\) elements and \(\tau\) is the set of \(n\)-tuple (attributes).

The rules we use to limit the space of allowed relations are called \emph{restrictions}.

This is the analog of using \verb|CREATE TABLE| in SQL. We are creating rules for 
the tuples inside the relation.

Also, this is just the definition of the name of the relations and the types of its attributes. 

\section{Constraint}

We denote that \(d[x]\) is a function from \(x \to R^+\), where \(R^+\) is the relation \(R\) without the attribute \(x\).
This is called the \emph{constraint}.

\section{Functional Dependencies}

A \emph{functional relation} is dependence between one or more attributes commonly noted \(A \to B\).

Formally, given \(\alpha \subseteq \mathrm{ident}(R)\) and \(\beta \subseteq \mathrm{ident}(R)\) and \(D \subseteq \dom(R)\)
\(\alpha \to \beta\), \(\beta\) is dependent on \(\alpha\) if

\[
    \forall d_1, d_2 \in D: d_1[\alpha] = d_2[\alpha] \implies d_1[\beta] = d_2[\beta].
\]

In simple terms the notation \( X \to Y\) means "we know \(Y\) if we know \(X\)".

A complete dependence is when \(A \to B\) is when we can not further reduce the tuple \(A\) 
so that we still get \(B\).

\section{Armstrong Axioms}

For a relation \(R = \{a_1, \dots, a_n\}\) with the schema \(\alpha, \beta, \gamma \subseteq \mathrm{ident}(R)\).

The Armstrong axioms are given: 

\begin{enumerate}[label = \Roman*.]

    \item \emph{Reflexivity:} for all \(\beta \subseteq \alpha\) holds \(\alpha \to \beta\)

    \item \emph{Transitivity:} \(\alpha \to \beta \land \beta \to \gamma \implies \alpha \to \gamma\)

    \item \emph{Connectivity:} \(\alpha \to \beta \implies \alpha \gamma \to \beta \gamma\)

    \item \emph{Union:} \(\alpha \to \beta \land \alpha \to \gamma \implies \alpha \to \beta \gamma\)

    \item \emph{Decomposition:} \(\alpha \to \beta \gamma \implies \alpha \to \beta \land \alpha \to \gamma\)

    \item \emph{Pseudotransivity:} \(\alpha \to \beta \land \beta \gamma \to \delta \implies \alpha \gamma \to \delta\)

\end{enumerate}

These are not strictly axioms, but they are called that way.

\subsection{Attribute Closure}

The \emph{attribute closure} \(AC(FD, x)\)is the set of all attributes reachable via functional dependency including 
the starting point.

\textbf{Example:}

\(R = \{A,B,C,D\}\) with \(FD = \{A \to B, B \to C, AB \to CD\}\).

\begin{itemize}

    \item \(AC(FD, A) = \{A, AB, ABC, ABCD\} = ABCD\)

    \item \(AC(FD, B) = \{B, BC\} = BC\)

\end{itemize}

\section{Canonical Cover}

We consider two sets of functional dependencies if and only if their 
attribute closures \(FD^+\) are identical.

For a schema \(R\) with a set of functional dependencies \(FD\) we denote \(FC^c\) as 
\emph{the canonical cover} of \(FD\) if the following criteria are satisfied: 

\begin{itemize}

    \item \(FD^c \cong FD\), \(FD^{c+} = FD^+\)

    \item For all \(\alpha \to \beta \in FD^c\) are minimal in the sense that 

        \subitem \(\forall a \in \alpha: FD^c \setminus (\alpha \to \beta) \cup (\alpha \setminus a \to \beta) \ne FD^c\)
        
        \subitem \(\forall b \in \beta: FD^c \setminus (\alpha \to \beta) \cup (\alpha \to \beta \setminus b ) \ne FD^c\)

    \item All left side attributes appear only one time 

\end{itemize}

The following steps are always performed for the whole set of functional dependencies one after the other.

\subsubsection*{Left-Reduction}

For all \(\alpha \to \beta \in FD\) check if there is a redundant \(a \in \alpha\). \(\beta \subseteq AC(FD, \alpha \setminus a)\).
If that is the case then replace \(\alpha \to \beta\) with \(\alpha \setminus a \to \beta\).

After that 

\subsubsection*{Right-Reduction}

For all \(\alpha \to \beta \in FD\) check if there is a redundant \(b \in \beta\). 
\(\beta \subseteq AC(FD \setminus \{\alpha \to \beta \} \cup \{\alpha \to \beta \setminus b, \alpha\})\).
If that is the case then replace \(\alpha \to \beta\) with \(\alpha \to \beta \setminus b\).

Then 

\subsubsection*{Elimination}

Remove \(\alpha \to \emptyset\).

And finally

\subsubsection*{Union}

If \(\alpha \to \beta_1\) and \(\alpha \to \beta_2\) then combine them into \(\alpha \to \beta_1, \beta_2\).

\textbf{Example:}

Given are \(R=\{ A, B, C, D, E, F \}, FD=\{ ABC \to DEF,A \to BC,D \to EF\} \).

\emph{Left-Reduction:}

First iteration, \(ABC \to DEF\)

\begin{itemize}
    
    \item Is \(A\) redundant? No: \(AC(F, BC) = BC\)
    
    \item Is \(B\) redundant? Yes: \(AC(F, AC) = AC \implies ABC \implies ABCDEF\).  
    Thus, we have \(AC \to DEF, A \to BC, D \to EF\).
    
    \item Is \(C\) redundant? Yes: \(AC(F, A) = A \implies ABC \implies ABCDEF\).  
    Thus, we have \(A \to DEF, A \to BC, D \to EF\).

\end{itemize}

\emph{Right-Reduction}

Using \(\{A \to DEF, A \to BC, D \to EF\}\) we proceed with the first dependency 
\(A \to DEF\).

\begin{itemize}
    
    \item Is \(D\) redundant? No, without it, we can not reach \(EF\).
    
    \item Is \(E\) redundant? Yes: \(AC(A \to DF, A \to BC, A \to EF, A) = A \implies ADF \implies ADEFBC\).  
    Thus, we have \(F = \{A \to DF, A \to BC, D \to EF\}\).
    
    \item Is \(F\) redundant? Yes: \(AC(A \to D, A \to BC, D \to EF, A) = A \implies ABC \implies ABCDEF\).  
    Thus, we have \(F = \{A \to D, A \to BC, D \to EF\}\).

\end{itemize}

\emph{Elimination and Union}

\[
    FC^c = \{A \to BCD, D \to EF\}
\]


Important notes:

\begin{itemize}
    
    \item By the left-reduction we only care about fd's which have at least two attributes on the right side.
    
    \item By the right-reduction we only care about the fd's with one attribute at the right.

\end{itemize}

\subsection{How to find a Candidate Key}

Given a set of attributes \(\{A,B,C,D\}\) with the following functional dependencies:

\[
    A \to B, C \to B, A \to D
\]

The set is already left-reduced. 

\begin{itemize} 
   
    \item \(AC(F, A) = ABD\)
    
    \item \(AC(F, C) = CB\)

\end{itemize}

We get \(A \to BD, C \to B\).

For the right reduction: 

\begin{itemize}

    \item Is \(B\) redundant? Yes

\end{itemize}

Finally, we get our candidate key \(AC \to ABCD\).

\subsection{Losslessness and Maintenance of Dependency}

Given a relation which needs to be split into more relations:

\begin{itemize}

    \item \emph{Losslessness:} After the split, the information in the original relation needs to be accessible via joins.

    \item \emph{Maintenance of Dependency:} The original functional dependencies do not change after the split.

\end{itemize}

\subsection{Normal Forms}

A \emph{normalized} table are protected from data inconsistencies and make the tables more readable.

\subsubsection*{I Normal Form}

\begin{itemize}
    
    \item No row order for information.
    
    \item No Mixing data types in the same column.
    
    \item No Tables without a primary key.
    
    \item No Repeating groups.

\end{itemize}

This normal is mostly given in relational algebra problems.

\subsubsection*{II Normal Form:} 

Each non-key attribute must depend on the entire primary key.

The relation is in the second normal form if it is already in the first normal form and each \textbf{non-key} attribute is functionally dependent on the \textbf{key-candidate}.

\textbf{Example I:}

\(R = \{A,B,C,D\}, \quad FD = \{A \to BC, B \to A\}\) not in 2NF due to \(D\) not being present.

\textbf{Example II:}

\(R = \{A,B,C,D\}, \quad FD = \{A \to B, B \to A, AD \to C\}\)

Candidates \(AD, BD\), not prime attribute \(C\). Thus, it obeys the 2NF.

\subsubsection*{III Normal Form} 

A schema \(R\) is in the 3NF if for all \( \alpha \to \beta \in FD\) at least one of the following statements 
is true: 

\begin{itemize}

    \item \(\alpha \to \beta\) is trivial \(\beta \subseteq \alpha\)

    \item \(\beta\) has only prime attributes 

    \item \(\alpha\) is a superkey 

\end{itemize}

The relation is in the third normal form if it is already in the second normal form and each \emph{non-key} attribute 
is not dependent on other \emph{non-key} attribute.
 
\subsubsection*{Boyce-Codd III Normal Form} 

A schema \(R\) is in the BCNF if for all \( \alpha \to \beta \in FD\) at least one of the following statements 
is true: 

\begin{itemize}

    \item \(\alpha \to \beta\) is trivial \(\beta \subseteq \alpha\)

    \item \(\alpha\) is a superkey 

\end{itemize}

Every attribute in a table should depend on the key, the whole key, and nothing but the key.
       
\textbf{Example I}

\(R = \{A,B,C,D\}, \quad FD = \{A \to BC, C \to D\}\), not in 3NF due to \(D\) being dependent on \(C\).

\subsubsection*{IV Normal Form} 

Multivalued dependencies in a table must be multivalued dependencies on the key.

\subsubsection*{V Normal Form} 

Our table in the forth normal form cannot be describable as the logical result of joining some other tables.

\subsection{Synthesis Algorithm}

The \emph{synthesis algorithm} transforms a relation schema into a set of schemas that are in Third Normal Form (3NF), 
while ensuring \emph{lossless join} and \emph{dependency preservation}. The algorithm proceeds as follows:

\begin{itemize}

    \item Compute the \emph{canonical cover} \(F_c\) of the given set of functional dependencies \(F\):

    \begin{itemize}

        \item Decompose all dependencies so that each has a single attribute on the right-hand side.

        \item Remove extraneous attributes from the left-hand sides.

        \item Eliminate redundant dependencies.

    \end{itemize}

    \item For each functional dependency \(\alpha \to \beta \in F_c\), construct a relation schema
   
    \[
        R_k = \alpha \cup \beta.
    \]
   
    All dependencies whose attributes are contained in \(R_k\) are associated with this schema.

    \item If none of the generated schemas contains a candidate key of the original relation, create an additional schema whose 
    attributes form a candidate key.

    \item If a schema \(R_k\) is completely contained in another schema \(R_m\), remove \(R_k\), since it is redundant.

\end{itemize}

\textbf{Example:}

Given

\[
    R = \{A, B, C, D, E\}
\]

with

\[
    F = \{ ADE \to BE,\; B \to ACD,\; D \to AC,\; ACE \to BD,\; C \to B \}.
\]

\emph{Step 1: Right-hand side decomposition}

\begin{align*}
    & ADE \to B,\quad ADE \to E,\quad B \to A,\quad B \to C,\quad B \to D, \\
    & D \to A,\quad D \to C,\quad ACE \to B,\quad ACE \to D,\quad C \to B
\end{align*}

\emph{Step 2: Left reduction}

\begin{itemize}

    \item \(ADE \to B\): \(A\) and \(E\) are extraneous since \(D^+ = \{D,B,A,C,E\}\), hence \(D \to B\).

    \item \(ADE \to E\) is trivial and removed.

    \item \(ACE \to B\): \(A\) and \(E\) are extraneous, yielding \(C \to B\).

    \item \(ACE \to D\): \(A\) and \(E\) are extraneous, yielding \(C \to D\).

    \item All other dependencies already have minimal left-hand sides.

\end{itemize}

Current set:

\[
    \{ D \to B,\; B \to A,\; B \to C,\; B \to D,\; D \to A,\; D \to C,\; C \to B,\; C \to D \}
\]

\emph{Step 3: Remove redundant dependencies}

\begin{itemize}

    \item \(D \to A\) is redundant since \(D \to C\) and \(C \to B\) and \(B \to A\).

    \item \(B \to C\) is redundant since \(B \to D\) and \(D \to C\).

    \item \(C \to D\) is redundant since \(C \to B\) and \(B \to D\).

\end{itemize}

Thus, the canonical cover is:

\[
    F_c = \{ B \to A,\; B \to D,\; D \to C,\; C \to B \}
\]

\emph{Step 4: Construct relation schemas}

\begin{align*}
    R_1 &= \{B, A\}, \\
    R_2 &= \{B, D\}, \\
    R_3 &= \{D, C\}, \\
    R_4 &= \{C, B\}
\end{align*}

\emph{Step 5: Remove redundant schemas}

None of these schemas is contained in another, so all are kept.

\emph{Step 6: Test for candidate keys}

For the original relation \(R = \{A, B, C, D, E\}\), attribute \(E\) does not appear on any right-hand side and must be part of 
every key.

\[
    (BE)^+ = \{A, B, C, D, E\}
\]

so \(\{B, E\}\) is a candidate key.

Since no schema contains \(\{B, E\}\), we add:

\[
    R_5 = \{B, E\}
\]

\textbf{Final 3NF Decomposition:}

\[
    \{ \{B,A\},\; \{B,D\},\; \{D,C\},\; \{C,B\},\; \{B,E\} \}
\]

\subsection{Decomposition Algorithm}

The \emph{decomposition algorithm} transforms a relation schema into Boyce-Codd Normal Form (BCNF) by repeatedly decomposing 
relations that violate the BCNF condition. A relation schema \(R\) is in BCNF if for every non-trivial functional dependency 
\(\alpha \to \beta\) on \(R\), \(\alpha\) is a superkey of \(R\).

\begin{itemize}

    \item If \(R\) is already in BCNF, stop

    \item Otherwise, choose a functional dependency \(\alpha \to \beta\) that violates BCNF, meaning \(\alpha\) is not a superkey of \(R\)

    \item Decompose \(R\) into two schemas

    \[
        R_1 = \alpha \cup \beta
        \quad\text{and}\quad
        R_2 = R \setminus (\beta \setminus \alpha)
    \]

    \item Apply the algorithm recursively to \(R_1\) and \(R_2\) until all resulting schemas are in BCNF

\end{itemize}

\textbf{Example:}

Given

\[
    R = \{A, B, C, D\},
\]

with

\[
    F = \{ A \to B,\; B \to C,\; C \to D \}.
\]

\textbf{Step 1: Check BCNF}

\(A \to B\) violates BCNF since \(A\) is not a superkey of \(R\)

\textbf{Step 2: First decomposition}

Using \(A \to B\), decompose into
\[
    R_1 = \{A, B\}
    \quad\text{and}\quad
    R_2 = \{A, C, D\}
\]

\textbf{Step 3: Check BCNF of \(R_1\)}

In \(R_1(A,B)\), \(A \to B\) holds and \(A\) is a key, so \(R_1\) is in BCNF

\textbf{Step 4: Check BCNF of \(R_2\)}

From \(B \to C\) and \(C \to D\), we obtain \(A \to C\) and \(A \to D\), but \(A\) is not a key of \(R_2\), so BCNF is violated by \(A \to C\)

\textbf{Step 5: Second decomposition}

Using \(A \to C\), decompose \(R_2\) into

\[
    R_3 = \{A, C\}
    \quad\text{and}\quad
    R_4 = \{A, D\}
\]

\textbf{Step 6: Check BCNF of remaining schemas}

In \(R_3(A,C)\), \(A\) is a key, so \(R_3\) is in BCNF

In \(R_4(A,D)\), \(A \to D\) holds and \(A\) is a key, so \(R_4\) is in BCNF

\textbf{Final BCNF Decomposition:}

\[
    \{ \{A,B\},\; \{A,C\},\; \{A,D\} \}
\]

\subsection{Optimization}

The following equivalences hold for relational algebra expressions: 

\begin{itemize}
    
    \item \(\sigma_{C_1 \land C_2 \land \dots \land C_n} \cong \sigma_{C_1} ( \sigma_{C_2} ( \dots ( \sigma_{C_n} (R)) \dots ))\)
    
    \item \(\sigma_{C_1} (\sigma_{C_2} (R)) \cong \sigma_{C_1} (\sigma_{C_2} (R))\)
    
    \item If \(L_1 \subseteq L_2 \subseteq \dots \subseteq L_n\) then 
        \[
            \pi_{L_1} (\pi_{L_2} ( \dots ( \pi_{L_n} (R)) \dots ) ) \cong \pi_{L_1} (R) 
        \]
    
    \item \(\pi_{A_1, \dots, A_n} (\sigma_{C} (R)) \cong \sigma_C ( \pi_{A_1, \dots, A_n}(R))\)
    
    \item \(\times, \cup, \cap\) and \(\bowtie\) are commutative
    
    \item Pushing Selections, select as early as possible \( \sigma_C \left(R \bowtie_{C_J} S \right) \cong \sigma_C (R) \bowtie_{C_J} S\)

    Special Case: 

    \[
     \sigma_{C_1 \land C_2} \left(R \bowtie_{C_J} S \right) \cong \sigma_{C_1} (R) \bowtie_{C_J} \sigma_{C_2} (S)
    \]

    \item \(\pi_L (R \bowtie_{C_J} S) \cong \pi_{A_1, \dots, A_n}(R) \bowtie_{C_J} \pi_{b_1, \dots, b_n}(S)\)
    
    \item \(\times, \cup, \cap\) and \(\bowtie\) are associative
   
    \item \(\sigma\) is distributive with \(\cup, \cap, \setminus\) 

    \[
        \sigma_C (R \Theta S) = \sigma_C (R) \Theta \sigma_C (S)
    \]
    
    \item \(\pi\) is distributive with \(\cup\) 

    \[
        \pi_C (R \cup S) = \pi_C (R) \cup \pi_C (S)
    \]
    
    \item De Morgam for Joins with selections 

    \[
        \neg (A \land B) = \neg A \lor \neg B \quad \neg (A \lor B) = \neg A \land \neg B
    \]
    
    \item \(\sigma_C (R \times S) \cong R \bowtie_C S\)

\end{itemize}
